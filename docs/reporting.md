# 面向用户的检查报告

目的：先帮助用户决定要处理什么，再提供可审计的技术证据。入口中的“Present a reader-first report”章节是 agent 的输出约定；检查脚本的 JSON、严重程度、规则编号和退出码不变。

## 示例：故障演示目录

以下是基于仓库构造样例的**报告表达示例**，不是改版后重新在 WorkBuddy 中执行的记录。正式报告应替换为该次调用的真实范围、命令、计数和证据。

### 结论

本次检查范围为 `examples/broken`，分析了 3 个技能入口：**1 项需要优先处理，2 项需要确认**。建议先补齐入口元数据，再核对缺失引用和重名。

### 需要优先处理

**入口缺少元数据**

- 位置：[no-metadata/SKILL.md:1](../examples/broken/no-metadata/SKILL.md#L1)。
- 发现：文件没有以 `---` 开始的元数据区块，不符合本次检查的入口约定。这不单独证明某个宿主一定加载失败。
- 建议：确认这个目录确实应作为技能使用后，补充包含 `name`、`description` 的元数据区块。

### 需要确认

**引用的文件不存在**

- 位置：[alpha/SKILL.md:7](../examples/broken/alpha/SKILL.md#L7)。
- 发现：链接指向的 `./references/missing.md` 不存在；如果后续步骤依赖它，可能缺少必要说明。
- 建议：先确认引用是否必需，再补齐文件或修改引用，不直接删除链接。

**两个入口声明了相同名称**

- 位置：[alpha/SKILL.md](../examples/broken/alpha/SKILL.md) 和 [beta/SKILL.md](../examples/broken/beta/SKILL.md)。
- 发现：两者都声明为 `deploy-review`。当前无法据此确定宿主会加载哪个，也不能判定存在语义冲突。
- 建议：确认它们是否应同时存在，再决定是否改名或保留两个版本。

### 下一步

这是故意包含问题的测试样例，不建议直接修复仓库原件。若要演练修复，应先获准复制到单独目录，在副本上修改并重新检查。真实技能则应逐项获得修复授权。

### 技术详情

从仓库根目录运行：

```sh
node skills/skill-lens/scripts/check.mjs examples/broken --json
```

预期退出码为 `1`，是检查器发现 error，不是检查器未能运行。规则为 `METADATA_MISSING (error)`、`REFERENCE_MISSING (warning)`、`NAME_COLLISION (warning)`，合计 1 error、2 warning、0 info。

在已声明的静态检查范围内没有操作性中断；`coverage.complete=true` 不表示全面安全、全宿主兼容或所有引用语法均已检查。

正式报告必须给出实际执行的命令；以上仓库相对命令只是示例，不能替代宿主安装目录中脚本的实际调用记录。进程退出码与 shell 包装器退出码不同的，应分别说明。

## 其他结果如何表达

- 没有发现：写“在本次规则范围内未发现问题”，不写“绝对安全”或“全部兼容”。
- 没有读到入口：写“未找到可读取的技能入口”，不写“所有技能通过”。
- 扫描不完整：把“未完成检查”及原因放在第一句，不用干净计数掩盖未检查部分。
- warning/info：保留原始等级，说明还需确认的内容，不擅自升级为故障。
- 大量发现：说明优先展示的条数和剩余数量，不让截断列表看起来像全部结果。

这些是提示词和验收要求，不是模型行为已经得到保证。仍应在目标宿主中以正常、故障、空目录和访问失败等情况进行人工验收。
